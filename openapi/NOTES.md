# Behaviour notes for client authors

Observations recorded while reading each route to author the spec. These are things a
client author needs and an OpenAPI document cannot express — timing, idempotency,
what to do on each error, and a few places where the implementation differs from what
a reader would reasonably assume.

## auth

- TOKEN TTLs, for the client's refresh scheduler: access token 900s (15 min, ACCESS_TOKEN_TTL_SECONDS); refresh window 30 days from SIGN-IN (REFRESH_TOKEN_TTL_SECONDS, which sizes the session row rather than being checked itself); grace window on a rotated-away refresh token 60s (REFRESH_GRACE_SECONDS). Store accessToken + refreshToken in the Keychain and refresh proactively a little before expiresAt.
- THE REFRESH WINDOW IS ABSOLUTE, NOT SLIDING, and `refreshExpiresAt` now says so. `user_session.expiresAt` is fixed when the row is created (NATIVE_SESSION_TTL_SECONDS = max(SESSION_MAX_AGE_SECONDS, REFRESH_TOKEN_TTL_SECONDS) = 30 days) and nothing ever writes it again — a rotation updates the token hashes, the grace deadline and lastSeenAt, and leaves the expiry alone. rotateRefreshToken rejects on that column, and both /auth/token and /auth/refresh return it verbatim, so the field counts down instead of sliding and a client may schedule re-authentication against it. (Until #123 it was recomputed as now + 30 days on every response, including refreshes that rotated nothing, so it advertised a session that renewed itself for ever and ended in an unexplained 401 at day 30.)
- ERROR BODIES FROM THESE THREE ROUTES USUALLY HAVE NO `requestId`. The 401 on /auth/token, the 400 and 401 on /auth/refresh, and both 429 variants are written inline with `NextResponse.json({ error: { code, message } })` — no requestId field. Only bodies produced by the error wrapper (the 500s) carry it. If `components.schemas.Error` marks `requestId` as required, a generated Swift client will throw a decoding error while handling a wrong password. It MUST be optional in that schema. (requestId is always available as the `x-request-id` response header.)
- The wrapper's 429 body USED to carry two fields inside `error` that were not in the Error schema — `retryAfterSeconds` (number) and `scope` (string). #124 removed both: the wait is read from the `Retry-After` header, and the limiter bucket name is a server-side diagnostic that is logged, not published. Both 429s reachable from /auth/token now have the same canonical `Error` shape; only their `message` wording and their headers differ.
- /auth/token can 429 from two different limiters with different budgets (the bodies are identical since #124, so only the `X-RateLimit-*` headers, which the second limiter does not set, distinguish them): the wrapper's api-mutation limit (60/min, keyed by IP only because defineV1Route supplies no getUserId) runs first, then the handler's `login:<ip>` LOGIN_LIMIT (10 attempts / 15 min, 15 min lockout) which is SHARED with the web credentials endpoint. A successful sign-in does not reset that bucket (resetRateLimit is never called), so 10 sign-ins per IP per 15 minutes is the real ceiling — relevant for shared NAT, office Wi-Fi and CI.
- All three routes inherit the default mutation limiter because defineV1Route passes no options — /auth/refresh and /auth/logout included, 60 POSTs per minute per IP across ALL v1 mutating routes combined. A resume-burst that fires many refreshes plus writes from one IP can trip it.
- The rate-limit store is an in-memory Map, per server instance, cleared on deploy. Limits are therefore inconsistent across a multi-instance deployment and a client should trust Retry-After rather than modelling the budget.
- /auth/token never returns 400 or 422. A missing, malformed or non-JSON body yields the same opaque 401 INVALID_CREDENTIALS, because undefined email/password fall through verifyCredentials as `null`. There is also no 403: verifyCredentials only returns null, it never throws a domain error, so nothing here maps through DOMAIN_ERROR_MAP.
- /auth/refresh returns 401 identically for unknown / revoked / expired / stale-version / replayed. Replay is deliberately NOT distinguished — telling an attacker "that token was already used" confirms they hold a real one. A replay outside the 60s grace window revokes the entire session, so a client must never keep a stale refresh token around to retry later.
- Concurrent refresh is safe and expected: only one caller wins the compare-and-swap and receives a new refreshToken; every other caller gets 200 with `refreshToken: null` and a valid access token. Client rule: if refreshToken is null, keep what you have; if it is a string, overwrite. Never write null or "" into the keychain.
- /auth/logout always returns 204, including anonymous, expired and already-revoked tokens, and it is idempotent. It never returns 401. The spec declares bearerAuth because the token is what makes the call do anything, not because the handler enforces it — a generated client should attach the token but treat sign-out as fire-and-forget and clear local state regardless of the outcome.
- Logout scope is read ONLY from a parsed JSON body (`{"everywhere": true}`). A query parameter, a form encoding, or any body that fails JSON.parse is swallowed by `.catch(() => null)` and silently degrades to this-device-only, with a 204 either way — an easy way for a "sign out everywhere" button to silently do nothing.
- Logging out revokes the session row, which also kills its refresh token: a subsequent /auth/refresh with that token returns 401 (pinned by tests/integration/native-auth.test.ts). `everywhere: true` additionally increments User.sessionVersion, which invalidates every outstanding access and refresh token for the user.
- Revocation is checked inside route handlers (contextFromRequest -> checkSession), but the edge middleware inspects only claims and `exp`. A revoked access token therefore still clears the edge until it expires — up to 15 minutes — and is refused by the route (401). Not client-actionable, but it is why the access TTL is short.
- A native access token carries NO club memberships, and never needs to (#250). The edge lets a signed-in caller through to any `/t/{slug}/**` route whose club the token does not list, and every tenant route resolves the membership — and the permission the route needs — from the database. So joining a club by booking there takes effect on the very next request, with no refresh.
- Not declared, but reachable in theory: Prisma's P2025 maps to 404 NOT_FOUND in toApiErrorResponse. /auth/refresh re-reads the session with findUniqueOrThrow AFTER rotation succeeds, and /auth/token calls findUniqueOrThrow on the user inside createUserSession, so a hard row delete racing either call surfaces as 404 rather than 401/500. It requires a destructive race, so I left 404 out of `responses`; a defensive client should treat any unexpected 4xx on refresh as "sign in again".
- Every response from these routes carries `X-API-Version` (currently `2026-04-29`) and `x-request-id`. The version header is a marker only — the server never branches on a request's version — but it is worth logging so a contract change is visible in client telemetry.
- Paths above are relative to the v1 base: the real URLs are /api/v1/auth/token, /api/v1/auth/refresh and /api/v1/auth/logout. Set `servers` accordingly.
- There are no path or query parameters on any of these three operations, so `parameters` is omitted rather than empty.

## venues

- `GET /venues/near` does NOT return `VenueSummary`. `nearVenues` runs a hand-written `$queryRaw` and returns `{id,slug,name,city,country,distanceKm,avgRating,reviewCount}` — no `sports`, no `fromPriceCents`, no `coverPhotoUrl`. Anyone assuming the list and geo endpoints share a model will generate a client that cannot render the same card from both.
- The radius parameter is named `radiusKm`, not `radius` (the task brief said "radius"). There is no `radius` parameter; sending one is silently ignored and the default 10 km is used.
- All caps are SILENT CLAMPS, never 400s: `/venues` `limit` -> clampLimit (default 20, max 50, sub-1 or NaN -> 20); `/venues/near` `radiusKm` -> clampRadiusKm (default 10, max 50, <=0 or NaN -> 10). That is why `data.radiusKm` is echoed — a client that asked for 500 km and does not read it back will report "nothing nearby" for a search it never ran.
- Three parameters reach the database unvalidated and therefore produce 500, not 400: `sport` on both `/venues` and `/venues/near` (cast `as never` straight into the Prisma enum filter / the `::"SportType"` cast), and `limit` on `/venues/near` (`Math.min(Number(limit) ?? 20, 50)` — `limit=abc` gives `LIMIT NaN`, `limit=-5` gives `LIMIT -5`). `/venues`'s own `limit` is safe because clampLimit absorbs NaN. I documented min/max/integer on these so a generated client cannot send garbage, but the server does not enforce them.
- `indoor` is evaluated as `sp.get('indoor') === 'true'`. Only the literal string "true" means indoor; `indoor=1`, `indoor=yes`, `indoor=TRUE` all filter for OUTDOOR resources. Omitting the parameter is the only way to not filter.
- `maxPrice=0` is silently dropped (the repository guards with a truthiness check), so it does not mean "free venues only". Same for a non-numeric value.
- Availability `?date=` is resolved in the VENUE's timezone via `fromZonedTime`, but `?from=`/`?to=` are parsed with bare `new Date()`. So `from=2026-09-24` is accepted and means UTC midnight, not local midnight at the club — a subtle two-hour skew for a Sofia venue that no error reports. Documented on the parameter.
- `?days=` is only read inside the `date` branch. Sent with `from`/`to`, or alone, it is silently ignored — not a 400.
- `RANGE_TOO_WIDE` (400) is thrown by `computeSlots`, which runs per resource. Two consequences: (a) it is unreachable via `date`+`days` because `days` is already capped at 14 by `parseDays`, so only `from`/`to` can trigger it; (b) for a venue with no matching ACTIVE resource the map body never runs, so an absurdly wide `from`/`to` returns 200 with an empty `resources` array instead of the error.
- An unmatched or foreign `?resourceId=` is a 200 with `resources: []`, not a 404. Only a missing/non-ACTIVE VENUE is a 404, and that check runs before the range is parsed.
- `VenueSummary.sports` and `fromPriceCents` are computed from the resources the query loaded. On `GET /venues` that include is `take: 20`; on `GET /venues/{id}` it is `take: 50`. A venue with more than 20 active resources can therefore advertise a different sport list and a higher `fromPriceCents` in the list than in the detail. Real behaviour, not a modelling choice.
- I wrote `VenueDetail` as a flat standalone schema rather than `allOf: [VenueSummary, ...]`, even though the TypeScript DTO uses `extends`. Swift/OpenAPI generators handle allOf inconsistently and the flat form decodes identically.
- `VenueResource.surface` is modelled nullable because `dto.ts` types it `string | null`, but the Prisma column `surface CourtSurface` is NOT NULL, so in practice it is always a string. Modelled nullable so a future nullable column cannot break decoding.
- `VenueDetail.openingHours` is `openingHoursJson` passed through verbatim with a TypeScript type of `unknown`. Nothing in the repo reads or writes a shape for it (the only two references are the DTO's own field and its assignment), so I left it as a free-form schema with no `type`. Do not let a generator invent a struct for it.
- `photos` and `amenities` ARE loaded by `getVenueById` (take 20 / take 30) but the DTO never serialises them. There is no photo list on the public API today — only `coverPhotoUrl`.
- `avgRating`, `lat` and `lng` are Prisma Decimals and would serialise as STRINGS without the `Number()` coercion in `dto.ts`. They are numbers on the wire today; that is a boundary invariant one careless edit could break, which is why I noted it in the field descriptions.
- Every money field is integer cents: `fromPriceCents`, `basePriceCents`, `priceCents`, and the `maxPrice` query parameter. Currency appears ONLY on `ResourceSlots.currency` in the availability response — neither `VenueSummary.fromPriceCents` nor `VenueResource.basePriceCents` carries one, so a client cannot format a price from the venue endpoints alone.
- No 429 on any of these. `resolveRateLimitScope` returns null for non-mutating methods before it reads its options, so GETs are never rate-limited; the repository caps are the only ceiling. I did not document a 429 response for that reason.
- Both `X-API-Version` and `x-request-id` are set on every response (success and error) by `withApiErrorHandling`. I declared them only on the 200s to keep the operations readable.
- The existing `openapi/playerz-v1.json` is a bare skeleton: `{openapi, info, paths:{}}` with no `components` at all. `#/components/schemas/Error` and the `bearerAuth` security scheme do not exist yet — whoever assembles the document must add them, or every `$ref` here dangles. `tests/guardrails/openapi-coverage.test.ts` checks route coverage plus the presence of `responses` and `security`; it does not resolve `$ref`s, so a dangling one would pass the guardrail and fail codegen.
- Slots overlap by design: a resource with `slotStepMinutes: 30` and `minBookingMinutes: 60` emits 09:00-10:00, 09:30-10:30, ... These are candidate start times, not a partition of the day. A client rendering them as a non-overlapping grid will double-count.
- An abandoned checkout holds its slot indefinitely: PENDING bookings block, `expiresAt` exists but nothing sweeps it, and the route deliberately does not filter expired PENDINGs out. So `available: false` / `blockedReason: "booked"` can mean "someone abandoned this an hour ago", and there is no field distinguishing that from a confirmed booking.
- `clubSlug` (T16) is on `VenueSummary` and `VenueDetail`, and it is the value `POST /t/{slug}/bookings` takes — NOT `slug`, which is the VENUE's slug and unique only within its club. Before it existed no public DTO carried a club slug, and the iOS client sent the venue slug to the booking route (VenueDetailModel.swift, `book`), which works only while a club names its venue after itself. `GET /venues/near` (`NearVenue`) still has no `clubSlug`: open the venue with `GET /venues/{id}` before booking. `venue.tenantId` is not a foreign key, so a venue can outlive its club row; such a venue is left out of `GET /venues` (a page may then hold one fewer than `limit`; the cursor is unaffected) and is a 404 on `GET /venues/{id}`.
- DURATIONS (Q16, #355). Each `available` slot carries `durations`: every length a booking starting there can have, shortest first, each with its `endTs` and its `priceCents`. Those prices come from `quoteBooking`, the function `POST /t/{slug}/bookings` prices with, so book with the `endTs` of the length the player chose and the charge is the number shown. A length is offered only if the whole span is free and inside one opening window; `ResourceSlots.maxBookingMinutes` caps them. A taken slot has no `durations`. Past slots are NOT filtered: a `date=` window for today still lists this morning, and booking one is 400 `SLOT_NOT_BOOKABLE` — hide `startTs <= now` on the client, as the web does.
- `publicSlug` (#355, P41) is on `VenueSummary` and `VenueDetail`: the web's `/venues/{publicSlug}`, unique across every club and never changed once set. The API itself still addresses venues by `id`; there is no `GET /venues/by-slug`.

## bookings

- POST /bookings returns 200 and 201 with IDENTICAL bodies. The only signal that a booking was created rather than replayed is the status code, so any generated client that collapses 2xx into one case loses the distinction. Source: `return ok(toBooking(created.row), { status: created.replay ? 200 : 201 })`.
- On an idempotent replay the request body is not consulted at all — `createBooking` finds the row by `(tenantId, idempotencyKey)` and returns it before validating or comparing anything. Reusing a key for a DIFFERENT slot silently returns the first booking, with no error. The route's own `quoteBooking` still runs first, so a replay whose body is invalid can still 400; but a replay whose body is valid-but-different succeeds and returns the original.
- `status` is modelled as an open string, not an enum, on purpose. The Prisma enum is PENDING/CONFIRMED/CANCELLED/COMPLETED/NO_SHOW and the DTO types it as `string`. A closed enum in the generated Swift client would throw on a status added server-side later, in a binary that cannot be hotfixed — the exact failure mode this codebase repeatedly designs against. If the generator's defaults make an open enum awkward, keep the open string.
- WHO ANSWERS 401 AND 403, since #250. The EDGE MIDDLEWARE (`src/middleware.ts`) answers 401 for an anonymous caller, and 403 `{"error":{"code":"FORBIDDEN","message":"Forbidden","details":{"requiredPermission":…}}}` only when the token LISTS the club with a role lacking the route's permission — in practice a web session, since native tokens list no clubs. Everything else is decided by the ROUTE, from the database, before the handler body runs: a caller with no ACTIVE membership gets 403 `{"code":"FORBIDDEN","message":"Forbidden"}` (no `details`, identical for a club that does not exist or one behind an Entra group gate the session has not cleared), a member whose role lacks the permission gets the same plus `details.requiredPermission`. The edge hand-writes its envelope with no `requestId`; the route's carries one. So `Error.requestId` must stay OPTIONAL in the shared schema or the edge's responses will fail to decode.
- The 429 body is not produced by `toV1ErrorResponse`, but since #124 it is the same shape: `{"error":{"code":"RATE_LIMITED","message":...}}`. No extra keys at the `error` level, and still no `requestId` — which is why `Error.requestId` must stay optional. `#/components/schemas/Error` is the right $ref for it.
- Rate limiting applies to the three POSTs only. `defineV1Route` passes no options, so the wrapper's default `API_MUTATION_LIMIT` (60 requests / 60s) applies to POST/PUT/PATCH/DELETE and `resolveRateLimitScope` returns null for GET — GET /bookings genuinely cannot return 429. Also, `defineV1Route` supplies no `getUserId` resolver, so the bucket is keyed by IP alone and is SHARED across every v1 mutation from that IP; behind carrier NAT that is shared across unrelated users. Worth flagging to whoever owns the mobile retry policy.
- The truncated-membership 500 that used to be listed here is gone (#250). It came from `contextFromRequest` resolving `tenantId: null` for a club missing from a truncated token list and `inTenant` then throwing `MissingTenantError`; the context now resolves the tenant from the database, so the token's list — truncated, stale or absent — no longer decides anything on these routes.
- POST /bookings needs a PLAYER account (#263): one account is one kind, and booking is playing. A club or coach account — or one the #263 migration left undecided — gets 403 `PLAYER_ACCOUNT_REQUIRED` at EVERY slug, its own club included, checked before the club is looked up so it discloses nothing about which clubs exist. This is the one error whose `message` is localised: it is written in the caller's stored `User.locale`, because "sign in with your player account" is the sentence they need. Switch on `code` all the same. Reads, cancels, checkouts and reviews of bookings an account already has are not refused — the migration kept a club account's old player bookings.
- GET /bookings answers a caller with NO membership at `{slug}` with 200 and an empty list, as its description always said; before #250 the edge refused that caller with 403 first, so the empty list was only reachable with a truncated token. POST /bookings admits a non-member and joins them; a club that is not ACTIVE, a SUSPENDED member and a club behind an Entra group gate the session has not cleared all get the 404 an unknown court gets.
- 402 INSUFFICIENT_CREDIT is deliberately NOT documented on checkout, despite `InsufficientCreditError` being mapped to 402. `spendCredit` computes `applied = Math.min(balance, amountCents)`, so the ledger's `next < 0` guard in `appendEntry` cannot fire from this route; both the balance read and the append run inside the same SERIALIZABLE transaction. Add it only if `spendCredit` ever stops capping.
- THE PILOT BOOKING MODEL (#354). A booking is CONFIRMED when made and paid at the club; `expiresAt` is null and checkout answers 409 `ONLINE_PAYMENT_DISABLED`. Only a club with `onlinePaymentEnabled` (none in the pilot, not settable from the app) still gets the PENDING hold + checkout flow, so branch on `status`. A player cancels until `Booking.cancellableUntil` (the venue's cutoff, default 24 h, measured in elapsed hours) and never after the start: 403 `CANCELLATION_CUTOFF_PASSED`. Staff with `bookings.view_all` are not bound. Three NO_SHOW bookings at a club in 90 days (by booking start, after the last time staff lifted the block) refuse new bookings there with 403 `NO_SHOW_BLOCKED`; an idempotent replay still returns the original. Both 403 messages are in the caller's `User.locale`. A slot that has already started is 400 `SLOT_NOT_BOOKABLE`.
- THE CAP ON UPCOMING ONLINE BOOKINGS (#380). Each club sets how many upcoming online bookings one player may hold there (`VenueOrg.maxUpcomingOnlineBookings`, default 3, 1–50, edited by OWNER/MANAGER on `/admin/pricing`, audited as `CLUB_ONLINE_BOOKING_CAP_CHANGED`). A new booking past it is 409 `BOOKING_LIMIT_REACHED` with `error.details = {"limit": n, "upcoming": m}` and a message in the caller's `User.locale`. This is the first domain error whose envelope carries `details`: `ErrorMapping.details` in `src/app/api/v1/_lib/errors.ts` reads them off the error instance. The count is the caller's CONFIRMED bookings (plus PENDING with an unexpired hold) at that club with `Booking.channel = ONLINE` and `startTs > now` — instants, so no timezone enters. Desk bookings and recurring series (`channel = DESK`) never count and are never limited. The check runs after the idempotent replay (a retry still gets its 200) and under a transaction-scoped advisory lock on (club, player), with the replay re-checked under the lock, so a burst of parallel requests from one player cannot exceed the cap and a same-key race returns the winner's booking instead of a 409. The code name is agreed with the venue page (#355); do not rename it.
- The cancel endpoint does NOT issue a refund. It writes a Cancellation receipt and returns the quote; `refundBooking` (the Stripe leg) is a separate use case that this route never calls. `refundAmountCents` is money DUE, not money moved — a client saying "refunded" would be lying. Verified by grep: no call site for `refundBooking` in the cancel route.
- `CancelQuote.reason` is server-generated prose describing the policy band (e.g. `26.0h before start (>= 24h)`), NOT the `reason` string the client submitted. The submitted reason is stored but not echoed anywhere in the response. This is an easy field to mis-bind in a client.
- On the checkout card path, `confirmed: false` does not mean the payment failed and does not mean it succeeded — confirmation happens later via the Stripe webhook. There is no polling endpoint in this set of routes, so the client needs its own strategy (re-fetch the booking and check `status`).
- `CheckoutSession.publishableKey` is `process.env.NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY ?? null`, so it can legitimately be null in a misconfigured environment while `confirmed` is false — the client then has a client secret it cannot use. Modelled as nullable and flagged in the field description.
- Since #354 the CreateBookingRequest body is parsed with zod (`src/app-layer/schemas/booking.ts`): `notes` is capped at 500 characters and a non-string `notes` is a 400 rather than silently dropped; `startTs`/`endTs` must be RFC 3339 date-times WITH an offset. Unknown body properties are still ignored (a `totalCents` sent by a client is not an error), so `additionalProperties: false` is still not set.
- I did not model `X-API-Version` / `x-request-id` on every single response, only on the 2xx and the 429 where the headers carry information a client acts on. In reality `withApiErrorHandling` stamps `x-request-id` and the version header on every wrapped response, including errors — the edge middleware's 401/403 are the exception, since they never reach the wrapper.
- `openapi/playerz-v1.json` in the repo is currently a placeholder (`{"openapi":"3.1.0","info":{"title":"placeholder","version":"0"},"paths":{}}`) with no `components` block at all, so I could not read the existing `Error` schema or the `bearerAuth` security scheme definition to confirm my assumptions about them. The coverage guardrail at /Users/user/git/playerz.bg/tests/guardrails/openapi-coverage.test.ts checks route coverage both ways plus the presence of `responses` and a `security` key — it does not validate schemas — and it currently fails on the placeholder until all v1 paths are assembled.
- Auth is `Authorization: Bearer <jwe>` via next-auth's `getToken`, which falls back to the header when no cookie is present. A token that verifies is not enough: `checkSession` is consulted on every request, and a revoked session degrades to anonymous, producing a handler-thrown 401 rather than a 403. That is why 401 is listed on routes the edge would normally have already rejected.
- `POST /bookings/{id}/review` can take up to ~10 s when it carries text: the classifier runs BEFORE the row is written, synchronously, with a 10 s timeout. Give that request a longer client timeout than the other booking calls, and do not retry it on a slow response. A retry that lands after the first attempt stored the review gets `409 ALREADY_REVIEWED`, which is harmless but reads as a failure.
- A `201` from the review endpoint is not "published". `data.status` is `PUBLISHED`, `PENDING_REVIEW` or `REJECTED`, and all three are successful submissions. Show `PENDING_REVIEW` as "waiting for a moderator", not as an error. A classifier outage lands there too, by design.
- Reviewing is only possible once a booking is `COMPLETED`, which a server job sets shortly after `endTs`. There is no `reviewable` flag on `Booking`. `status == "COMPLETED"` is the signal, and `409 ALREADY_REVIEWED` is how a client learns the venue already carries this player's one review.

## tenant

- GET /t/{slug}/me no longer returns 403 (#250). The edge used to answer 403 for a non-member whose token listed other clubs but not this one; it cannot tell that caller from one who joined this club since signing in, so it now lets the request through and the handler answers 404 for both — and for a club behind an Entra group gate the session has not cleared. The 403 response was removed from the spec.
- Error.requestId is absent on several real responses even though the shared Error schema lists it. The /me handler builds its 401 and 404 with a bare NextResponse.json and passes no requestId; all middleware-originated 401/403 bodies likewise omit it; and the 429 body omits it too. The x-request-id response HEADER is still set on everything that goes through the API wrapper (not on middleware responses). A generated client must not require requestId to be present.
- The 429 body IS the Error shape since #124: buildTooManyRequestsResponse (src/lib/security/rate-limit-middleware.ts) emits error.code and error.message and nothing else. It still carries no requestId, so Error.requestId must remain optional. The retry hint is the Retry-After header, which is the only place it lives now.
- Middleware-originated errors (401/403) carry neither X-API-Version nor x-request-id, because the Edge runtime cannot import the Node-only wrapper. I declared those headers only on responses that provably pass through withApiErrorHandling.
- membership.status is always "ACTIVE" today: the query filters `status: 'ACTIVE'`, so any other status yields the 404. I enumerated the full MembershipStatus domain and said so in the description rather than narrowing the enum to one value.
- Enum brittleness, worth a codegen decision: role, status and locale are enumerated from the Prisma schema, which is accurate, but a Swift generated enum fails to decode an unknown value if a role is ever added. permissions is deliberately NOT enumerated for that reason even though it is a closed set server-side.
- tokenStale changed meaning in #250. It used to be true whenever the token's claim for this slug disagreed with the database — INCLUDING when the token had no claim for it, which is every native token on every call, and a refresh could never clear it because refresh mints no claims. It is now true only when the token LISTS this club with a tenant id or role the database disagrees with, the one case where the edge still acts on a claim (it refuses, from the listed role, a mutation that role lacks). A native client will always see false and has nothing to do.
- POST /t/{slug}/connect/onboarding reads no request body whatsoever — the handler never calls req.json(). I omitted requestBody entirely. A generated client method should take no body parameter; anything sent is silently ignored, and returnUrl/refreshUrl are built server-side from NEXTAUTH_URL.
- The onboarding 404 comes from Prisma P2025 on findUniqueOrThrow, translated by toApiErrorResponse (not by DOMAIN_ERROR_MAP) into NOT_FOUND with the message "Resource not found or already deleted". Since #250 the membership is read from the database a moment before, so it takes a club deleted between those two reads — a race, but genuinely reachable, so it stays declared.
- MissingTenantError (inTenant called with a null tenantId) is deliberately absent from DOMAIN_ERROR_MAP and would surface as a 500. It is unreachable on this route: the route's permission (`admin.billing_manage`) is enforced by `contextFromRequest`, which refuses a caller with no membership before a context without a tenant can exist. I did not document it as a 500 cause for that reason.
- NEXTAUTH_URL is read as `process.env.NEXTAUTH_URL ?? ''`. If it is unset, the return/refresh URLs are built as relative paths and Stripe's accountLinks.create will reject them, producing a 500. Configuration issue rather than a contract one, but it is how a misconfigured environment fails here.
- Rule 4 (money as integer cents) is not exercised by either of these two operations — neither returns a monetary value.
- Neither operation is versioned in its path segment here; the spec path is /t/{slug}/... while the real route is /api/v1/t/{slug}/..., so the document's servers entry must carry the /api/v1 prefix for the generated client to hit the right URL.
- GET /me carries no 429: resolveRateLimitScope returns null for any non-mutating method before it reads the options, so reads are not rate-limited by this wrapper at all.

## me

- `GET /me` and `GET /me/bookings` (T16) address NO club: no slug, no permission, only a session. The edge passes them (no slug in the path) and the handler answers 401 itself, with `requestId`, through the error envelope — unlike `GET /t/{slug}/me`, whose 401 is hand-built.
- `GET /me` sends `landing.reason` and NOT the web path the server lands on. Map the reason to a screen of your own; the web's paths (`/t/{slug}/admin/calendar`, `/me/bookings`, `/`) are its routing and will move. The decision is the one `/start` and the site header use (`decideLanding`), read in one transaction with the account, so `accountKind` and `landing.reason` always agree: PLAYER→`player`, CLUB→`club` or `club-unavailable`, COACH→`coach`, null→`undecided`.
- `accountKind: null` is UNDECIDED, not "unknown": an account that held club roles at several clubs, or a coach role, when kinds arrived (#263). Its `landing.club` is its highest-ranked live club (OWNER over MANAGER over STAFF, then oldest), or null.
- `reason: "coach"` has `landing.club: null` today because there is no coach UI anywhere; the web lands a coach on the player UI. When a coach home exists the club it lands on will appear here with `role: "COACH"`.
- `GET /me/bookings` is `listMyBookings`, the use case behind the web `/me/bookings` page, mapped by `toMyBookingDto` — the mapper the page's server render is to share. Each item is a `Booking` plus `clubSlug` (what cancel, checkout and review take for that booking), `venueReview` (the caller's one review of that VENUE, possibly left against another booking there) and `canReview` (COMPLETED and no review of the venue yet — decided server-side).
- Paging: newest `startTs` first, keyset by booking id. `limit` is clamped to 1..100, default 20; `limit=abc` and `limit=0` are the default, not a 400. A cursor that no longer names a booking yields an empty page.
- `PATCH /me` (#359) sets the display name and the sports played, each with a self-declared level 1–7 (Q37), and answers the whole account like `GET /me`. Replace your copy with the answer: the server trims the name and collapses inner spaces, and returns `sports` in a stable order (the sport enum's), not the order you sent. `sports` is the WHOLE list: one you leave out is deleted, `[]` clears them all. Unknown properties are a 400 with `details.field` naming the property, so a client cannot change `email`, `accountKind`, `locale` or `avatarUrl` through it, by accident or otherwise. A CLUB account gets 403 `PLAYER_ACCOUNT_REQUIRED` for `sports` and nothing is written, the name included. The level is the player's own claim, kept in an owner-only table (`player_sport_level`, RLS on `app.user_id`, P43); no other account can read it yet.
- `GET /me` now carries `avatarUrl` (the sign-in provider's picture, read-only) and `sports` (`[]` until set). The web's token carries the name the header shows, so after a `PATCH` that changes it the web refreshes its session; a native client reads the name from `GET /me` and has nothing to refresh.
- `GET /me/bookings?when=upcoming|past` (#359) is the web's Предстоящи and Минали tabs. `upcoming` is PENDING or CONFIRMED with `endTs` still ahead (a game in progress is upcoming until it ends), soonest first; `past` is everything else, newest first, so a booking cancelled for next week is under `past` at once. The split is computed at request time, so a booking can move from one list to the other between two pages of a scroll: re-read page one when the screen reappears. Omitting `when` keeps the old single list. Any other value is 400 `BAD_REQUEST`, `details.field: "when"`.
- `MyBooking` now documents `cancellableUntil`, which the server has sent since #354: it was in `Booking` and missing here.
- `GET /me/bookings/{id}` (#359) is `getMyBooking`, the use case behind the web's booking detail page, mapped by `toMyBookingDetailDto`. Someone else's booking and a made-up id are the same 404 `NOT_FOUND`. `venue` adds `addressLine`, `city`, `lat`, `lng` (numbers), `phone` and `publicSlug`; directions on the web are a Google Maps link built from the venue name, address and city, and a native client can hand `lat`/`lng` to MapKit instead. `payAtClub` is true for every pilot club: show `totalCents` as paid at the club. `players` is display names and avatars only, booker first; until #358 it is the caller alone.
- Cancelling from the detail screen is still `POST /t/{clubSlug}/bookings/{id}/cancel`. Disable the action once `cancellableUntil` is behind the device clock, but treat a 403 `CANCELLATION_CUTOFF_PASSED` as the same state: the server's clock decides, and the deadline can pass while the screen is open. The web shows the venue's `phone` then, for the player to call the club.
- `409 VIEWER_CHANGED` is declared on both because both are read by the web's client data layer with `x-playerz-viewer`; a native client never sends that header and never gets it.

## sso

- GET is NOT paginated. The handler calls `ok(mappings.map(toGroupMapping))`, so the body is `{"data": [ ... ]}` — a bare array inside `data`, not `page()`'s `{"data":{"items":[...],"nextCursor":null}}`. `listGroupMappings` takes at most 200 rows and gives no truncation signal. A reader who assumed the list rule in the brief applied here would generate an undecodable client.
- `"role": "OWNER"` returns 400 with code `BAD_REQUEST` (Zod enum), NOT `ROLE_NOT_MAPPABLE`. `RoleNotMappableError` → 400 `ROLE_NOT_MAPPABLE` exists in DOMAIN_ERROR_MAP and is thrown by `assertMappable()` in src/app-layer/usecases/entra-group-mappings.ts, but the schema rejects OWNER first on both POST and PATCH, so that code is unreachable through these two routes today. It is documented on both operations anyway because the use case is also reachable from seeds/jobs.
- All validation failures on POST/PATCH surface as code `BAD_REQUEST` (ValidationError sets code `BAD_REQUEST`, not `VALIDATION_ERROR`) with `details` = `{"issues": [ ... ]}` — the raw Zod issue array, not the flattened `{path, code, message}` shape that `toApiErrorResponse` builds for an uncaught ZodError.
- There is no 404 for an unknown or non-member `slug` on any of the four — it is 403 `FORBIDDEN`, and an unknown club answers exactly as a club you are not in does, deliberately, to avoid a tenant-enumeration oracle. On GET the handler's message covers both and a member without `sso.manage` too; on the mutating verbs a member without it additionally gets `details.requiredPermission`. The only 404 is `MAPPING_NOT_FOUND` on PATCH/DELETE.
- 401 and 403 can be emitted by the EDGE middleware (src/middleware.ts `apiError`) rather than the route: 401 for an anonymous caller, 403 on a mutating verb when the token lists the club with a role lacking `sso.manage` (`details: {"requiredPermission": "sso.manage"}`). Those bodies have `error.code` and `error.message` but NO `requestId` and no `X-API-Version` header, so `requestId` must stay optional in the shared Error schema. Since #250 every other refusal comes from the route, from the database — including a non-member's, which carries no `details`.
- 429 is real on POST/PATCH/DELETE (the wrapper rate-limits every mutating method by default with `API_MUTATION_LIMIT`; it can only be disabled by env). GET is never rate-limited — `resolveRateLimitScope` returns null for non-mutating methods. The 429 body is `{"error":{code, message}}` — the canonical Error shape, with no `requestId`. Read `Retry-After` for the wait.
- 409 on POST is normally `DUPLICATE_GROUP_MAPPING`, but it degrades to the generic `CONFLICT` if `pgErrorCode()` cannot find SQLSTATE 23505 in the driver error graph (Prisma 7 nests it at a varying depth); `toApiErrorResponse`'s P2002 branch then produces 409 `CONFLICT` with `details` = the constraint target. Clients should treat both 409 codes as "already mapped".
- PATCH has no 409: `aadGroupId` is not in the update schema, so no unique constraint can be hit. A body whose only key is `aadGroupId` is stripped to `{}` and fails the empty-PATCH refine with 400 — it does not silently no-op.
- `aadGroupId` is lower-cased by the schema transform, so the created/returned value can differ from what the client sent. `aadGroupName` cannot be cleared once set (null is rejected; omission means "leave unchanged").
- `id`/`mappingId` are cuids (Prisma `@default(cuid())`), not UUIDs — do not let a generator type them as UUID.
- The response `role` is typed as plain `string` in `GroupMappingDto`; I modelled it as the 4-value enum because the schema, the use case, the sync and a P27 CHECK constraint all exclude OWNER. If that CHECK is ever dropped and an OWNER row appears, a strict generated enum decoder would fail on the list response.
- No money fields on these routes, so the integer-cents rule does not apply here.
- openapi/playerz-v1.json is currently a placeholder (`{"openapi":"3.1.0","info":{"title":"placeholder","version":"0"},"paths":{}}`) and defines neither `Error` nor `bearerAuth` yet; tests/guardrails/openapi-coverage.test.ts requires every exported v1 method to have an operation, so the merged spec must also define those components and cover the other routes before that test passes.

## realtime

- The 429 body on POST /realtime/token is the canonical Error shape and $refs Error. src/lib/security/rate-limit-middleware.ts builds it as {error:{code,message}} — still no requestId, so a shared Error schema that made requestId required would break a generated Swift client on every 429. The separate RateLimitError schema that used to describe the old body is gone (#124).
- POST /realtime/token is rate limited even though nothing in the route file says so: defineV1Route delegates to withApiErrorHandling with no options, and that wrapper applies API_MUTATION_LIMIT (60 req / 60 s) to POST by default. The route passes no getUserId resolver, so the bucket key degrades to <scope>:ip:<ip>:anon — every signed-in user behind one egress IP shares one budget. Relevant because a native client refreshing every 15 minutes is a recurring POST.
- The 500 on /realtime/token is real, not boilerplate: contextFromRequest performs a database session lookup (checkSession) on every call, so an outage there surfaces as INTERNAL.
- /realtime/token returns url: null when NEXT_PUBLIC_CENTRIFUGO_URL is unset — the token is still minted and the status is still 200. Likewise, mintConnectionToken falls back to an empty CENTRIFUGO_TOKEN_SECRET when the variable is unset, producing a well-formed but worthless token with no error of any kind. Neither misconfiguration is observable to the client as a failure status.
- The handler for /realtime/token never reads the request body, so I declared no requestBody. An empty POST is correct.
- On /realtime/subscribe I marked x-centrifugo-secret, user and channel as required because Centrifugo always sends them and the endpoint is unusable without them — but at runtime none of them produces a 4xx when absent. The route answers HTTP 200 with the standard deny body instead, including when the JSON body fails to parse. Flagging this because 'required' here documents the contract, not an enforced validation.
- error.code in the Centrifugo deny body is an INTEGER (403 / 503), while error.code everywhere else in this API is a string. Anyone merging these operations into a spec with a shared error convention should not normalise it.
- /realtime/subscribe is the only route in this pair that is not wrapped by defineV1Route, so it emits neither X-API-Version nor x-request-id, and it is not rate limited. src/lib/api-version.ts explicitly lists 'anti-enumeration uniform-200 responses' among the intentionally exempt routes, which is what this is.
- I tagged /realtime/subscribe with both 'Realtime' and 'Internal'. If the generator emits one client class per tag, consider dropping 'Realtime' from it so the broker proxy does not end up on the client's realtime API surface — the operation description says not to generate a client for it, but a tag is what a generator actually acts on.
- The guardrail at tests/guardrails/openapi-coverage.test.ts requires BOTH directions (every exported method described, no phantom paths) plus a responses key and a security key on every operation. Both operations here satisfy it. The spec path spellings /realtime/token and /realtime/subscribe match its toSpecPath() derivation exactly.
- openapi/playerz-v1.json is currently the placeholder {"openapi":"3.1.0","info":{"title":"placeholder","version":"0"},"paths":{}}, so components.schemas.Error does not exist in the file yet. My operations reference it as instructed; whoever assembles the document must supply it, or these $refs dangle.
- Neither endpoint involves money or timestamps, so the cents and RFC 3339 rules did not apply. expiresInSeconds is a duration in seconds (900), not a date-time — worth stating because the name reads like it could be a deadline.
- Bearer is what a native client will use on /realtime/token, but contextFromRequest resolves the caller via next-auth getToken, which also accepts a browser session cookie. The single bearerAuth entry is accurate for the generated client and does not describe the cookie path.

## browser requests (session cookie)

- A native client is unaffected by everything in this section: it sends `Authorization: Bearer` and no session cookie, and no `Sec-Fetch-Site` or `x-playerz-viewer` header.
- 403 `CROSS_SITE_REQUEST`, on EVERY v1 route that resolves its caller through `contextFromRequest` (all of them except /auth/token, /auth/refresh and /realtime/subscribe): a POST, PUT, PATCH or DELETE that carries the next-auth session cookie (`next-auth.session-token`, `__Secure-` on HTTPS, `.0`/`.1` chunks) and a `Sec-Fetch-Site` header other than `same-origin` or `none` is refused before the token is read. `same-site` is refused too — SameSite=Lax sends the cookie from a sibling subdomain. A request with no `Sec-Fetch-Site` passes (curl, server-to-server, an old browser). Moving web writes from Server Actions, which check `Origin` themselves, to cookie-authenticated v1 fetches is what made this necessary; before it nothing under `/api/v1` looked at where a request came from. Not retryable from the page that got it. Source: `src/app/api/v1/_lib/request-guard.ts`.
- 409 `VIEWER_CHANGED`: the web client sends `x-playerz-viewer: <user id the page was rendered for>` on every v1 call from a page that shows a person's own data. When the session is live and belongs to a different user — a second account signed in from another tab, routine since #263 — the request is refused before the membership is read and nothing is written. The cure is a reload. A signed-out or revoked caller is NOT a viewer change; it gets the route's own 401. Not declared per operation in the spec, because no generated client sends the header.
- Both are checked before the handler body, so neither is ever accompanied by a side effect: no booking, no review, no moderation decision, and no platform audit row (the integration suite asserts each — `tests/integration/api-v1-cross-site.test.ts`).
